## 一、核心价值（为什么需要 LLM）

### 1.1 关键认知：编辑器解决的是"怎么画"，LLM 解决的是"画什么"

当前工具的画图功能已经足够方便——建房间、放门窗、拖家具，操作直观。
但用户的核心问题不是"我不会画图"，而是：

| 用户真实困惑 | 编辑器能解决吗 |
|-------------|--------------|
| "5岁男孩的儿童房应该放哪些家具？" | ❌ |
| "床放东墙还是西墙？有什么区别？" | ❌ |
| "1.5m 的床放得下吗？衣柜 60cm 够不够？" | ❌ |
| "这个布局合理吗？有没有问题？" | ❌ |
| "还有别的摆法吗？哪个更好？" | ❌ |
| "我该选方案 A 还是 B？" | ❌ |

**画图工具解决的是 How——怎么画出来。用户缺的是 What 和 Why——画什么、为什么这样画。**

这不是"输入方式"的问题（打字 vs 拖拽），是**专业知识缺口**的问题。

### 1.2 LLM 的不可替代价值：设计顾问，不是输入法

LLM 接入不是为了让用户"不用鼠标"，而是让工具从**画板**变成**设计师**：

| 角色 | 传统编辑器 | 加入 LLM 后 |
|------|-----------|------------|
| 用户说 | 我知道要什么，我画出来 | 我有个房间想改造，你帮我看看 |
| 工具回答 | 提供画布和工具 | 提问题、给建议、出方案、解释理由 |
| 用户得到 | 一个自己画的图 | 一个比自己懂设计的朋友给的方案 |

**LLM 不是用来替代鼠标的，是用来替代"你不知道该画什么"的那份迷茫。**

### 1.3 三条核心价值

**价值 1：补全专业知识缺口**

普通用户不知道标准家具尺寸、不知道布局规则、不知道什么方案才算合理。
LLM 可以在这些地方补位：
- "次卧改儿童房" → 自动补全适合的家具清单和尺寸
- "床不要靠窗" → 理解这是一个硬约束，而不是一个偏好
- "想要学习氛围" → 推断为"书桌靠窗、采光优先"

**价值 2：提供决策依据，建立信心**

用户付费 9.9 元/月，买的不是"能画图"，而是**有人担保"这样是对的"**：
- 每个方案附带说明"为什么这样摆"
- 方案对比时解释 trade-off（"方案 A 通道更宽，方案 B 储物更多"）
- 硬约束检查结果可视化（✓ 床不靠窗、✓ 通道 65cm、✓ 衣柜门可打开）

**价值 3：覆盖模板覆盖不了的场景**

预设模板只能处理标准尺寸的标准房间。真实用户的需求千奇百怪：
- "2.7m×3.3m 的狭长书房，窗户在短边"
- "出租屋单间，要同时当卧室和客厅用"
- "保留了旧衣柜 160×55，加新家具"

LLM 让工具的适用场景从 N 个模板扩展到无穷多种真实户型。

### 1.4 这个认知如何影响产品定位

```
从: "AI 家居设计工具"     → 一个帮你画图的工具
到: "AI 家居设计顾问"     → 一个帮你做设计决策的顾问
```

LLM 的价值定位变了：

| 维度 | 如果核心是"省去操作" | 如果核心是"提供专业知识" |
|------|---------------------|------------------------|
| LLM 角色 | 输入转换器（自然语言→JSON） | 设计顾问（理解需求、给建议、解释方案） |
| 用户付钱买 | 省去拖拽的方便 | 省去专业知识的稀缺 |
| 竞品防御 | 功能堆砌就能抄 | 需要设计知识+Prompt+求解器的整合 |
| 定价依据 | 工具订阅（便宜） | 咨询服务（值钱） |
| 用户心理 | "挺方便的" | "帮我做了决定" |

### 1.5 不变的原则

LLM 仍**不做布局决策**。布局计算由约束求解器（纯 JS）完成。
LLM 的职责是：理解用户 → 提取结构化需求+偏好 → 为求解器提供参数 → 向用户解释方案。

```
用户需求 → [LLM：设计顾问] → 结构化数据+偏好参数 → [约束求解器] → 方案 → [LLM：解释] → 用户
                ↑                                                           ↓
                └────────────── 对话迭代（文字修改，增量更新）──────────────────┘
```

## 二、背景与目标

### 2.1 现有设计回顾

项目已明确定位 LLM 的角色（决策 D03）：

> **LLM 只做"自然语言→结构化数据"的翻译，不做布局决策。**  
> 布局决策由约束求解器（纯 JS）完成。

即现有数据流：

```
用户输入(自然语言) → LLM解析 → 结构化JSON → 约束求解器 → 布局方案 → 渲染
```

### 2.2 本文件要解决的问题

"个性化定制"超出了简单的结构化数据提取。用户说的不是参数，而是**意图、偏好和生活方式**。本文件定义：

1. **个性化定制的含义**——在什么维度上做定制，做到什么程度
2. **用户如何表达偏好**——交互方式设计
3. **LLM 如何理解偏好**——Prompt 工程与结构化方案
4. **技术实现路径**——分阶段落地建议

## 三、个性化定制的维度

将"个性化"分解为以下可操作的维度，按从结构化到模糊排序：

| 维度 | 示例 | 确定性 | LLM 角色 | 当前支持度 |
|------|------|--------|----------|-----------|
| **D1 空间约束** | "3m×4m 房间"、"门在北墙偏左" | 高（事实） | 提取数值 | ✅ 已有 |
| **D2 功能需求** | "需要床、书桌、衣柜" | 高（清单） | 提取清单 | ✅ 已有 |
| **D3 空间关系约束** | "床不要靠窗"、"衣柜贴墙角" | 中高（条件） | 翻译为约束规则 | ⚠️ 部分 |
| **D4 布局偏好** | "喜欢宽敞"、"要动静分离" | 中（主观） | 推断偏好向量 | ❌ 待设计 |
| **D5 生活方式** | "经常在家办公"、"有小孩" | 中（场景） | 推断功能优先级 | ❌ 待设计 |
| **D6 美学风格** | "简约风"、"原木色" | 低（审美） | 生成风格描述 | ⏸ 延后 |
| **D7 隐性需求** | "不要看起来太挤" | 低（模糊） | 结合常识推理 | ⏸ 延后 |

### 3.1 MVP 覆盖范围

**Phase 1a（LLM 验证阶段）覆盖 D1-D3**，这是产品路线图中已有的计划。  
**本方案新增：Phase 1b 覆盖 D4-D5**，在验证 D1-D3 准确率达标后，扩展 LLM 的理解维度到偏好和场景。

D6-D7 延后到验证数据支撑后再启动。

### 3.2 偏好向量的定义

D4-D5 的核心是将主观描述转化为可计算的偏好向量：

```typescript
interface PreferenceVector {
  // 空间利用倾向 (0=极致紧凑, 1=极致宽敞)
  spaciousness: number;  // 0.0 ~ 1.0

  // 分区倾向 (0=功能混杂, 1=严格分区)
  zoning: number;        // 0.0 ~ 1.0

  // 靠墙偏好 (0=随意摆放, 1=全贴墙)
  wallHugging: number;   // 0.0 ~ 1.0

  // 采光优先级 (0=不敏感, 1=必须靠窗)
  daylightPriority: number; // 0.0 ~ 1.0

  // 动线复杂度 (0=最少移动, 1=动线最优)
  circulation: number;   // 0.0 ~ 1.0

  // 功能场景标签
  scenarios: ScenarioTag[];
  // 'home_office' | 'child_safe' | 'pet_friendly' |
  // 'reading_nook' | 'guest_ready' | 'minimalist'
}
```

这个向量不是由用户直接填写，而是由 LLM **从自然语言中推断**，然后传递给约束求解器作为软约束参数。

## 四、用户交互设计

### 4.1 整体流程

```
┌─────────────────────────────────────────────────────────┐
│  ① 用户描述需求（自由文本 / 模板引导 / 逐项填写）         │
│     ↓                                                    │
│  ② LLM 理解与确认（展示解析结果，用户确认或修改）          │
│     ↓                                                    │
│  ③ 生成方案（3 套，差异化策略由偏好向量驱动）              │
│     ↓                                                    │
│  ④ 浏览方案（展示+特点说明+匹配度标签）                   │
│     ↓                                                    │
│  ⑤ 反馈迭代（"床换个方向" / "这个好但书桌位置不对"）       │
│     ↓  ↙ ↘                                                │
│  ⑥a 文字微调 ← 回到②                                 │
│  ⑥b 拖拽微调（PC 独有路径）                          │
└─────────────────────────────────────────────────────────┘
```

### 4.2 三种输入模式

用户进入时有三种方式表达需求，**不强制任何一种**：

| 模式 | 入口 | 适合用户 | 设计要点 |
|------|------|---------|---------|
| **自由文本** | 主输入框（已存在） | 知道要什么、能说清楚 | 自动补全引导、模板提示 |
| **逐步引导** | "一步步帮我" 按钮 | 不太确定、需要启发 | LLM 以问答形式收集信息 |
| **从模板修改** | 预设模板卡片（已存在） | 快速开始 | 选择模板后进入文本修改 |

#### 3.2.1 自由文本输入（已有，增强）

当前已有的输入框加上以下增强：

**输入前**——placeholder 示例轮播：
```
"3m×4m 儿童房，北墙有门，南墙有窗，需要床、书桌、衣柜"
"次卧改书房，3.3m×2.5m，靠窗放书桌，留出放沙发床的空间"
"出租屋单间改造，4m×4m，床靠墙，要有学习和吃饭的区域"
```

**输入中**——渐进式感知反馈：
- 输入框下方实时显示"已识别到：房间尺寸✓ 家具清单✓ 约束条件..."（防抖 800ms）
- 用户可以看到 LLM 正在理解什么，缺什么

**输入后**——解析结果确认卡（见 4.3）

#### 3.2.2 逐步引导模式（新增）

当用户输入模糊或点击"一步步帮我"时，进入 LLM 驱动的交互式问答：

```
用户: "帮我设计儿童房"
  ↓
LLM: "好的！我来帮您一步步规划。
  ① 房间尺寸是多少？（长 × 宽）
  ② 门和窗分别在哪个位置？
  ③ 需要放哪些家具？
  您可以直接回答，也可以先告诉我房间是给多大孩子用的。"

用户: "3m×4m，北门南窗，孩子 6 岁"
  ↓
LLM: "好的，6 岁男孩的房间，那需要预留玩耍空间。
  除了床、书桌、衣柜，还需要放玩具架或小书架吗？"

...
```

**设计原则**：
- LLM 一次只问 1-2 个问题，不抛清单
- 每个回答后展示当前已收集的信息摘要
- 用户随时可以说"就这样，生成方案"
- 所有对话历史在步骤②的确认卡中可编辑

#### 3.2.3 从模板修改（已有，增强）

当前 4 个模板卡片点击后，不直接创建房间，而是：

1. 在输入框中填入模板对应的自然语言描述
2. 用户可自由编辑文字
3. 点击"生成"后走 LLM 解析流程

```
点击"儿童房 4m×3m" → 输入框填入：
"4m×3m 儿童房，北墙中间有门，南墙有窗，需要床(120×200)、
 书桌(100×50)、衣柜(80×60)"

用户可以改为：
"4m×3m 儿童房，北墙中间有门80cm，南墙有窗150cm，
 需要床和书桌，不要衣柜，要放玩具架"
```

### 4.3 解析结果确认卡（新增核心交互）

LLM 解析完成后，不直接生成方案，而是先展示**确认卡**，让用户看到 LLM 的理解并修正。

```
┌──────────────────────────────────────────────────────┐
│  ✅ 已理解您的需求，看看我理解得对不对：              │
│                                                      │
│  🏠 房间: 4m × 3m                                   │
│  🚪 门: 北墙中间 80cm                               │
│  🪟 窗: 南墙居中 150cm                              │
│                                                      │
│  🪑 家具:                                            │
│     🛏️ 床 120×200 ×1                               │
│     📝 书桌 100×50 ×1                               │
│     📚 书架  80×30 ×1                               │
│                                                      │
│  ⚠️ 约束条件:                                        │
│     ✓ 床不要靠窗                                     │
│     ✓ 书桌靠窗放                                     │
│     ⚠️ "想要学习氛围" → 已识别为：书桌区域采光优先   │
│                                                      │
│  [✏️ 修改] [✅ 没问题，生成方案]                     │
└──────────────────────────────────────────────────────┘
```

**关键设计要点**：

1. **可编辑每一项**：点击 ✏️ → 对应的字段变为可编辑（支持文本或选择）
2. **偏好可视化**：偏好向量用直观方式展示（标签/滑块/图标），而非数字
3. **不确定性标记**：LLM 不确定的地方用 ⚠️/❓ 标记，优先让用户确认
4. **修改即重新解析**：用户修改后，局部字段更新，不需重新调用 LLM（前端直接修改 JSON）

**修改模式交互**：

```
用户点击"床不要靠窗"旁边的 ✏️
  ↓
展开约束编辑：
  ┌────────────────────────────┐
  │ 约束: 床不要靠窗           │
  │                           │
  │ [删除此约束]              │
  │ [+ 添加约束]              │
  │                           │
  │ 常见约束:                 │
  │  ○ 床靠墙放               │
  │  ○ 书桌靠窗               │
  │  ○ 衣柜贴墙角             │
  │  ○ 门前留空               │
  └────────────────────────────┘
```

### 4.4 方案展示中的个性化表达

方案卡片在现有基础上增加"匹配度"信息：

```
┌──────────────────────────────────┐
│  方案 A  ★ 推荐                  │
│                                  │
│  ┌─── 平面图 ───┐               │
│  │              │               │
│  │              │               │
│  └──────────────┘               │
│                                  │
│  特点: 家具贴墙放, 中间宽敞       │
│  ✓ 通道 65cm  ✓ 床不靠窗         │
│                                  │
│  📊 匹配您的需求:                │
│  宽敞度 ██████░░ 80%            │
│  采光   ███████░ 90%            │
│  分区   ████░░░░ 50%            │
│                                  │
│  说明: 书桌靠窗采光好,            │
│  但牺牲了部分分区感              │
└──────────────────────────────────┘
```

**设计要点**：
- 匹配度条让用户直观看到"方案和我的偏好契合度"
- 说明文字解释权衡（trade-off），让用户理解为什么这样布局
- 不追求 100% 匹配，而是展示多样性

### 4.5 反馈迭代交互

用户看完方案后，有多种方式迭代：

#### 方式 A：文字修改（全平台）

```
用户: "方案 A 不错，但把床换到东墙，书桌靠窗"

→ 回到 LLM 解析层，增量更新约束
→ 重新生成 3 套方案
→ 保留修改历史，可回退
```

#### 方式 B：局部反馈（新增）

用户可以针对某套方案的某个点给反馈：

```
在方案卡片上:
  "书桌位置不太对" → 点击 → 弹出浮层选择:
    ○ 书桌应该靠窗
    ○ 书桌应该靠墙  
    ○ 书桌换个方向
    ○ 自定义...
```

这种交互**不需要重新调用 LLM**——反馈直接映射为约束调整，约束求解器重新计算即可。

#### 方式 C：拖拽微调（PC 独有，已有）

保持已有方案，不做改动。

### 4.6 个性化记忆（未来扩展）

**Phase 4 后考虑**：当用户多次使用后，系统可以记住偏好：

- 用户上次调整的方向（"这个人喜欢书桌靠窗"）
- 用户反复否定的布局模式
- 同一用户的历史方案

实现方式：localStorage 存储用户偏好向量历史，新会话时作为 LLM prompt 的上下文。

## 五、LLM 技术方案

### 5.1 架构总览

```
┌──────────────┐    ┌──────────────────────────────┐    ┌──────────────┐
│  用户输入     │ →  │  LLM 解析服务                  │ →  │  结构化 JSON  │
│  (自由文本/   │    │  (浏览器端/云端)               │    │  + 偏好向量   │
│   问答记录)   │    │                              │    └──────┬───────┘
└──────────────┘    │  ┌──────────────────────────┐ │           │
                    │  │  Layer 1: 意图分类        │ │           ▼
                    │  │  确定输入类型、完整度       │ │    ┌──────────────┐
                    │  ├──────────────────────────┤ │    │  确认卡渲染    │
                    │  │  Layer 2: 结构化提取      │ │    │  (前端展示)    │
                    │  │  房间/门窗/家具/约束       │ │    └──────┬───────┘
                    │  ├──────────────────────────┤ │           │
                    │  │  Layer 3: 偏好推断        │ │           ▼ 用户确认
                    │  │  推断偏好向量、场景标签    │ │    ┌──────────────┐
                    │  └──────────────────────────┘ │    │  约束求解器   │
                    └──────────────────────────────┘    │  (纯前端 JS)  │
                                │                       └──────┬───────┘
                                ▼                              ▼
                      ┌──────────────────┐            ┌──────────────┐
                      │  LLM 调用缓存     │            │  多方案渲染   │
                      │  (相同输入命中    │            │  (3套差异化)  │
                      │   不重复调用)     │            └──────────────┘
                      └──────────────────┘
```

### 5.2 LLM 调用时机

| 时机 | 触发条件 | 调用内容 | 成本 |
|------|---------|---------|------|
| 初始解析 | 用户提交文本 | 完整 prompt（Layer 1+2+3） | 一次 |
| 引导问答 | 用户选"一步步帮我" | 多轮对话（上下文累积） | 多轮 |
| 确认后修改 | 用户修改确认卡字段 | 仅 JSON 字段编辑（无需 LLM） | 零 |
| 新增约束性修改 | 用户改文字描述 | 增量 prompt："原输入：... 修改：..." | 一次 |
| 局部反馈 | 用户点"书桌位置不对" | 不调 LLM，直接映射为约束调整 | 零 |
| 方案切换/重新生成 | 用户点击"重新生成" | 同一次解析结果，不同随机种子 | 零 |

**核心优化**：LLM 只调用一次（初始解析），后续迭代尽可能通过前端调整 JSON 实现。

### 5.3 Prompt 工程策略

#### 4.3.1 三层 Prompt 结构

**Layer 1 — 意图分类与完整性检查**

```typescript
const SYSTEM_PROMPT_L1 = `你是一个家居设计助手。分析用户的输入，判断：
1. 输入是否包含完整的房间信息（尺寸+门窗+家具）。
2. 如果信息不全，列出缺失的字段。
3. 输入的类型：全新需求 / 对已有方案的修改 / 模糊咨询。
4. 用户的专业程度：新手 / 有一定概念 / 清楚知道自己要什么。

以 JSON 格式输出。`;
```

输出示例：
```json
{
  "inputType": "new_request",
  "completeness": "partial",
  "missingFields": ["room_width", "room_height"],
  "userExpertise": "novice",
  "suggestGuidance": true
}
```

**Layer 2 — 结构化信息提取**

```typescript
const SYSTEM_PROMPT_L2 = `从用户的家居设计需求描述中提取结构化信息。
要求：
- 单位默认厘米，如果用户输入米则自动换算
- 门窗位置用相对墙段的百分比或偏移量表示
- 家具如果没有指定尺寸，使用常识默认尺寸
- 约束条件用结构化规则表示
- 所有距离单位使用厘米(cm)

输出严格的 JSON 格式，不要包含任何其他文字。`;
```

**Layer 3 — 偏好推断（新增）**

```typescript
const SYSTEM_PROMPT_L3 = `基于用户描述，推断其布局偏好和生活方式。

从以下维度分析：
1. spaciousness（宽敞度）：用户是否强调"宽敞"、"不挤"、"留出空间"
2. zoning（分区）：用户是否提到"动静分离"、"功能区"、"学习区"
3. wallHugging（靠墙偏好）：用户是否说"靠墙"、"贴墙"、"中间留空"
4. daylightPriority（采光优先级）：用户是否提到"靠窗"、"采光好"、"明亮"
5. circulation（动线）：用户是否关心"走路方便"、"开门不挡"
6. scenarios（场景标签）：从描述中推断使用场景

对每个维度给出 0-1 的置信度分数和推断依据。
如果信息不足以判断某个维度，设为 null。`;
```

#### 4.3.2 联合调用策略

**方案 A（推荐 MVP）：顺序调用 L1→L2→L3**

```
一次 API 调用，三层逻辑放入同一条 prompt，要求模型分步骤输出。

优点：一次调用，延迟最低，成本最低
缺点：偏好推断可能受前面步骤影响（顺序偏差）

适用：Phase 1a-1b
```

**方案 B（备选）：独立调用 L1, L2+L3**

```
先调用 L1 做意图分类 → 根据结果决定是否继续
再调用一次完成 L2+L3 的结构化输出

优点：可提前拦截无效输入，节省成本
缺点：两次调用增加延迟

适用：Phase 2+ 当调用量增大后
```

### 5.5 容错与降级策略

| 场景 | 处理方式 | 用户感知 |
|------|---------|---------|
| LLM 调用失败（超时/网络） | 使用本地规则提取（正则+关键词） | 可能精度下降，但流程不中断 |
| 解析 JSON 格式错误 | 重试 1 次；仍失败则 fallback 到规则提取 | 无感知 |
| 关键字段缺失 | 确认卡中高亮标记缺失项，引导补充 | 用户看到"需补充信息"标签 |
| LLM 返回不合理的数值 | 前端校验 + clamp（家具尺寸不超过房间、门窗位置在墙范围内） | 数值自动修正，标注"已调整" |
| 用户描述极端模糊 | L1 检测到 → 触发引导模式 | 见 4.2.2 引导流程 |
| API Key 配额耗尽 | 降级到本地规则引擎 + 缓存的常见布局模板 | 提示"AI 解析暂不可用，使用智能推荐" |

### 5.6 LLM 调用实现方案对比

| 方案 | 实现方式 | 延迟 | 成本 | 隐私 | 复杂度 |
|------|---------|------|------|------|--------|
| **A. 浏览器端直接调用** | 前端 fetch → LLM API | 1-3s | 按 token 计 | 数据直达 API，不经过第三方 | 低 |
| **B. Vercel Edge Function** | 前端 → Edge Function → LLM API | 1-3s | 同上 + Edge 运行费 | 可隐藏 API Key | 中 |
| **C. 自建后端代理** | 前端 → 后端 → LLM API | 2-4s | 同上 + 服务器 | 完全控制 | 高 |

**推荐：Phase 1a-1b 用方案 A，上线后切换方案 B。**

- Phase 1a 是离线验证，直接在脚本中调用 API 即可
- Phase 1b 用户测试阶段，前端直接调用 API（API Key 走环境变量注入）
- 上线前切换到方案 B 或 C，保护 API Key 不被客户端获取

### 5.7 请求合并与缓存策略

```
输入文本 → (MD5 hash) → 查缓存
  ├─ 命中 → 返回缓存结果（零延迟、零成本）
  └─ 未命中 → 调用 LLM → 写入缓存 → 返回

缓存 key = MD5(用户输入文本 + 语言)
缓存值 = LLMOutput（完整 JSON）
缓存位置 = localStorage（会话级）+ 可选 IndexedDB（持久级）
有效期 = 7 天
```

**收益**：用户反复测试同一描述时不重复调用；相同输入的不同用户共享缓存（方案 B/C 时可用服务端缓存）。

### 5.8 增量修改处理

当用户修改部分文本时，不需要重新做完整解析：

```
原输入: "3m×4m 儿童房，北墙中间有门80cm..."
修改: "把床换到东墙"

→ 增量 Prompt:
"原始输入：{originalInput}
原始解析结果：{previousLLMOutput}
用户的修改要求：{modificationText}

请基于原始解析结果，应用用户的修改，输出完整的更新后 JSON。
尽量保持其他字段不变。"
```

这种方式比重新完整解析更节省 token，且结果更稳定（修改部分不会影响已确认的字段）。

## 六、偏好向量如何影响布局

### 6.1 偏好 → 约束求解器参数映射

偏好向量不直接输入约束求解器（求解器只认硬约束），而是转化为**软约束权重**和**生成策略参数**：

```
偏好向量              →  约束求解器参数
───────────────────────────────────────
spaciousness=0.8      →  comfort_zone_width = 40cm (默认20cm)
                        furniture_gap = 30cm (默认20cm)

zoning=0.7            →  enable_zoning = true
                        zone_min_area = 2.0 m²

wallHugging=0.9       →  wall_preference_weight = 0.9
                        center_placement_penalty = 0.3

daylightPriority=0.8  →  window_buffer_zone = 50cm
                        desk_window_score_bonus = 0.4

circulation=0.6       →  min_passage_width = 90cm (默认80cm)
                        door_clearance = 120cm (默认100cm)
```

### 6.2 多方案差异化策略

三套方案的差异不应是随机的，而应该由偏好向量驱动的策略分支：

```
偏好向量 (spaciousness=0.6, zoning=0.8, wallHugging=0.7, ...)
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ 方案A: 推荐    │  │ 方案B: 分区   │  │ 方案C: 探索   │
│              │  │              │  │              │
│ 严格遵循偏好   │  │ 在偏好上做     │  │ 在偏好附近    │
│ 的"安全"方案   │  │ 一个有意的     │  │ 做一次"冒险"  │
│              │  │ 极端版本      │  │ 尝试         │
│ 满足所有      │  │ 例如偏好的     │  │ 用户可能没    │
│ 显式约束+     │  │ zoning 更高   │  │ 想过但会      │
│ 偏好方向      │  │ 的方案        │  │ 喜欢的方案    │
└──────────────┘  └──────────────┘  └──────────────┘
```

例如，如果用户偏好墙 hugging=0.7：
- 方案 A：70% 家具靠墙，30% 不靠（严格匹配偏好）
- 方案 B：90% 靠墙（极端靠墙，用户可以看到"更紧凑"的效果）
- 方案 C：40% 靠墙（探索性方案，用户可能发现"留点空间更好"）

**这样保证三套方案有意义的差异化，且每个方案都有被选中的理由。**
