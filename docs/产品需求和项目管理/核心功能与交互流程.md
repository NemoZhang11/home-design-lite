# home-design-tool — 核心功能与交互流程

> 本文档定义 MVP 阶段的功能规格、用户旅程和设备分工。配合《产品定位与路线图》和《风险评估报告》阅读。

---

## 一、用户核心旅程

### 主流程（一次典型使用）

```
入口（打开页面）
  │
  ▼
① 输入需求 ────────────────────── 手机/PC 均可
  │  "3m×4m 儿童房，北墙中间有门80cm，南墙有窗150cm，
  │   需要床(120×200)、书桌(100×50)、衣柜(80×60)，床不要靠窗"
  │
  ▼
② AI 解析 + 自动布局 ────────── 等待 2-5 秒
  │  后台：LLM解析→约束求解→生成3套方案
  │
  ▼
③ 浏览方案 ──────────────────── 手机/PC 均可
  │  左右/上下滑动切换方案
  │  每套方案标注关键尺寸和特点
  │
  ├── ✅ 满意 → 导出/截图保存（付费）
  │
  └── ❌ 不满意
        │
        ▼
      ④ 修改需求 ─────────────── 手机/PC 均可
        │  "床挪到窗户那边"
        │  "衣柜换个方向"
        │
        ▼
      ⑤ AI 重新生成 ────────── 回到③
```

### 为什么是这个流程

- ①→②→③ 三步完成核心价值，**不强制用户注册、不强制学习编辑器**
- 修改需求（④→⑤）不需要拖拽，改文字即可重新生成
- PC 用户多一条路径：方案不满意时，可以手动拖拽微调

### PC 独有路径

```
② (AI 生成方案后)
  │
  ▼
③' 手动微调 ─────────────────── 仅 PC
  │  进入编辑器模式
  │  拖拽家具位置、旋转方向
  │  修改墙段
  │
  ▼
③ 返回方案浏览
```

## 二、功能模块清单

### P0 — MVP 必须（Phase 3 交付）

| 功能 | 描述 | 优先级 | 设备 |
|------|------|--------|------|
| 需求输入 | 文本输入框，可输入自然语言描述 | P0 | 全部 |
| 方案展示 | 俯视 2D 平面图，渲染房间+门窗+家具+尺寸标注 | P0 | 全部 |
| 多方案切换 | 至少 3 套布局方案，可切换对比 | P0 | 全部 |
| 方案标注 | 每套方案显示关键尺寸（通道宽度、离墙距离） | P0 | 全部 |
| 需求迭代 | 用户修改文字描述，重新生成方案 | P0 | 全部 |
| 一键生成房间 | 按输入尺寸生成矩形房间+门窗 | P0 | 全部 |
| 家具目录 | 预设家具（床/书桌/衣柜/椅子/沙发/书架） | P0 | 全部 |

### P1 — 核心体验（Phase 3 含部分，Phase 4 补全）

| 功能 | 描述 | 优先级 | 设备 |
|------|------|--------|------|
| PC 微调模式 | 拖拽家具、旋转、删除 | P1 | 仅 PC |
| 方案导出 | 保存为 PNG 图片 | P1 | 全部 |
| 付费解锁 | 6+ 方案、无水印导出 | P1 | 全部 |
| 联盟商品链接 | 方案内家具挂载商品链接 | P1 | 全部 |

### P2 — 延后（视数据决定）

| 功能 | 描述 | 触发条件 |
|------|------|---------|
| 自定义家具 | 用户输入自定义尺寸和名称 | 用户留存 > 20% |
| 历史方案 | 保存/回顾历史方案 | 用户主动需求 > 30% |
| 移动端微调 | 手机端基础编辑能力 | 手机流量 > 70% |
| 户型拍照导入 | 手机拍照自动识别房间轮廓 | Phase 4 数据正向 |

### 明确不做（任何时候）

- 3D 渲染
- 施工图/水电图
- 社交/社区
- 用户账号系统（MVP 不做）
- 微信小程序 / 独立 App

## 三、输入格式规范

### 用户输入示例

```
好的： "3m×4m 儿童房，北墙中间有门80cm，南墙有窗150cm，
        需要床(120×200cm)、书桌(100×50cm)、衣柜(80×60cm)，床不要靠窗"

好的： "次卧改儿童房，长3.3m宽2.45m，门在北边靠左60cm处80cm宽，
        窗在南边100-245cm，保留东墙衣柜160×55，加儿童床和书桌"

差的： "帮我设计一个房间"（缺少尺寸信息 → 引导用户补充）
```

### 最小必要输入

如果用户输入信息不全，系统需引导补充：

```
系统：已识别到需要 [床、书桌]，但缺少以下信息：
  □ 房间尺寸（长 × 宽）
  □ 门的位置和宽度
  □ 窗户的位置和宽度
请补充以上信息，或点击「快速模板」使用标准尺寸：
  → 3m×4m 标准次卧（带门窗）
  → 2.5m×3m 标准书房
  → 自由输入
```

│  床不靠窗: ✓                             │

### 三方案差异化策略

| 维度 | 方案 A（靠墙） | 方案 B（分区） | 方案 C（居中） |
|------|---------------|---------------|---------------|

| 书桌位置 | 靠窗 | 西墙 | 东墙 |
| 空间感 | 紧凑 | 动静分离 | 四面通路 |
| 适合 | 小房间 | 功能分区 | 宽敞房间 |

## 六、API 设计（编辑器接口层）

将当前 demo 封装为可编程接口，供编排引擎调用：

```typescript
interface EditorAPI {
  // 房间
  createRoom(width_m: number, height_m: number): void;
  clear(): void;

  // 建筑元素
  placeDoor(wall: 'north'|'south'|'east'|'west', offset_m: number,
            width_m: number, swingInward?: boolean): void;
  placeWindow(wall: 'north'|'south'|'east'|'west',
              offset_m: number, width_m: number): void;

  // 家具
  addFurniture(type: string, x_m: number, y_m: number,
               rotation_deg?: number): void;
  removeFurniture(index: number): void;
  moveFurniture(index: number, x_m: number, y_m: number): void;
  rotateFurniture(index: number, deg: number): void;

  // 布局
  runAutoLayout(furniture: FurnitureItem[]): LayoutResult[];
  getCurrentState(): RoomState;

  // 方案
  loadScheme(json: SchemeData): void;
  exportImage(): Promise<Blob>;
}
```

**实现方式**：在现有 demo IIFE 中暴露 `window.__editorAPI`，约 50 行改造。

## 七、数据流

```
┌──────────────┐    ┌──────────────────┐    ┌──────────────┐
│  用户输入     │ →  │  LLM 解析层      │ →  │  结构化数据   │
│  (自然语言)   │    │  (离线/在线API)   │    │  JSON         │
└──────────────┘    └──────────────────┘    └──────────────┘
                                                   │
                                                   ▼
┌──────────────┐    ┌──────────────────┐    ┌──────────────┐
│  方案渲染     │ ←  │  约束求解引擎     │ ←  │  约束列表     │
│  (Konva 画布) │    │  (纯前端JS)      │    │  + 家具定义   │
└──────────────┘    └──────────────────┘    └──────────────┘
       │
       ▼
┌──────────────┐
│  用户浏览     │
│  / 微调       │
│  / 导出       │
└──────────────┘
```

**关键原则**：LLM 只做"自然语言 → 结构化数据"的翻译。布局决策由约束求解器（纯 JS）完成，不依赖 LLM 判断空间关系。这样可以：
1. 降低每次方案的 API 成本（LLM 只需要调一次解析）
2. 布局结果确定可复现（同一输入 → 同一输出）
3. 离线模式下仍可工作（缓存解析结果后，布局计算不依赖网络）
